# P2ray · 长任务架构（防跑偏）

> **为什么存在**：这个仓库的工作是跨会话、跨批次推进的。执行者（AI）会跑偏、会自称完成、会忘目标。
> 所以控制必须**外部化、文件化、可判据化** —— 不靠"记得"，靠"必须过"。
> 规则出处：`universal-architecture v2.1.3` §9（门禁）与 §17（长任务目标锁与防跑偏）。

## 文件分工

| 文件 | 是什么 | 什么时候读 |
|---|---|---|
| `goal.md` | **目标合同**六项：目标 · 验收命令 · 约束 · 预算 · 停手条件 · 版本 | 开跑前；任何改目标时 |
| `gates.md` | **门禁**：每条验收命令 + 判据 + 谁跑 + 不过怎么办 | 收工前；发版前 |
| `next.md` | **只写一个动作**（长任务不许列表式 next） | 每轮开始与结束时 |
| `state/goals/*.tsv` | **台账**：每轮一行（时刻 · 单元 · 命令 · 退出码 · 关键输出 · 判定） | 续跑时读最后一行 |
| `decisions/adr_*.md` | **决策记录**：为什么这么选，试过什么，代价是什么 | 想推翻某个设计前 |
| `scripts/arch-gates.ps1` | **判据本体**：G1–G5 逐条跑，输出 PASS/FAIL/SKIP | 由人或 CI 跑，**不由执行者自评** |

## 三条硬规矩

1. **验收命令由脚本跑，不由执行者自评。** 执行者的"我验证过了"不构成证据；
   证据是 `arch-gates.ps1` 的退出码与逐条结论。
2. **没有新鲜证据，就没有"完成"。** 不许拿上一轮的输出、不许"应该能过"。
3. **改目标先停手。** 停当前单元 → 写 ADR → 人批准 → 同回合更新 `goal.md` 与 `next.md`。
   不许边跑边改。

## 黄灯词

`应该 / 大概 / 看起来 / 我印象里` —— 出现即回读 `gates.md`，没有对应命令就先去写命令。
