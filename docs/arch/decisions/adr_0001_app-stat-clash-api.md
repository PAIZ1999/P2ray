# ADR 0001 · 按应用统计改用 clash API + 端口归因

## 背景

「按应用」最初用 ETW（`Microsoft-Windows-Kernel-Network`）过滤"回环 + 本地代理端口"的事件，
以为这样能拿到"哪个程序走了代理、走了多少"。实现上线后用户反馈"按应用统计不对"。

## 证据（实测，不是推断）

| 观测 | 数据 |
|---|---|
| 内核实际转发 | clash API 累计下行 4,016,940 字节 |
| ETW 收到的事件 | 2,720 条（采集本身是通的） |
| 通过"回环 + 代理端口"过滤 | 24 条 |
| 回环事件里最大的 5 条 | size = 2 / 2 / 6 / 6 / **52** 字节 |
| 按应用表新增 | 0 行 |

结论：**Windows 的 ETW 内核网络事件不上报回环连接的批量数据**，只剩握手包。
"筛回环事件 = 走代理的流量"这个前提不成立 —— 不是参数没调好，是路子不对。

## 决策

「按应用」改为与「按域名」同源：

1. 从 clash API `/connections` 取每条连接的 `metadata.sourcePort` 与精确 `upload/download`；
2. 用 `netstat -ano` 建「本地端口 → PID」映射（每秒刷新，缓存），把连接归因到进程名；
3. 连接首次出现时已有字节记为"待归因"，端口暂不可解析时保留在该连接上，下一轮再试。

## 代价

- **仅代理流量**：口径从"全机（含直连）"变成"仅代理"，与「按域名」一致；直连不再计入。
- **不再需要管理员权限**（ETW 需要）。
- **只支持 clash API 内核**（sing-box / mihomo）；Xray 下这两页为空，界面给提示。
- **短连接会漏计**：采样式，4 秒的突发的捕获率约 20%；20 秒的持续传输实测 99.996%。

## 已知局限

- 端口在连接关闭前都没解析出进程名时，那部分字节会丢弃（连接消失后 netstat 也查不到）。
- ETW 会话残留（进程被强杀）会污染后续采集；已在 `Start()` 前用 `logman stop` 清理，
  但这是绕过现象，不是根治。

## 若日后要改回 ETW

必须同时满足：能证明 ETW 在当前 Windows 版本上上报回环批量数据（给出 size>0 的大包事件），
否则本 ADR 的结论依然成立。
